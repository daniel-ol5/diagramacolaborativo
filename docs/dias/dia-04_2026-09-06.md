## 1. Qué se construye hoy, sin jerga

Hasta ahora ModelCollab era invisible. Había un servidor que sabía guardar diagramas,
decidir quién puede tocar qué y responder por WebSocket — pero nada que un humano
pudiera mirar. Hoy aparece **el lienzo**: la pantalla donde se ven las clases.

Conviene entender qué se dibuja exactamente, porque no es un dibujo libre.

Una clase en UML no es una caja con un nombre: es una caja con **tres compartimentos**.
Arriba el nombre, en el medio los atributos (los datos que guarda), abajo los métodos
(lo que sabe hacer). Y cada atributo y cada método lleva delante un símbolo que dice
quién puede acceder a él: `+` público, `-` privado, `#` protegido, `~` de paquete.

```
┌─────────────────────────┐
│        Cliente          │   ← nombre (en cursiva si es abstracta)
├─────────────────────────┤
│ - id: UUID              │   ← atributos, con la PK subrayada
│ - nombre: VARCHAR       │
│ - telefono: VARCHAR     │
├─────────────────────────┤
│ + registrar(): void     │   ← métodos, con firma y tipo de retorno
│ + buscarPorTelefono()   │
└─────────────────────────┘
```

Eso no es estética. Es **notación estándar**, y el tribunal la conoce. Una herramienta
de modelado que dibuja cajas con nombres y nada más no es una herramienta de modelado.

### De dónde salen los datos

De ningún lado nuevo. El lienzo lee **los mismos tres diagramas de referencia** que se
congelaron el Día 1 — barbería, veterinaria e inventario — que son los mismos archivos

## 2. La decisión que parece un detalle y no lo es

**No se copió ni un archivo de diagrama dentro de `web/`.**

La tentación era obvia: los diagramas viven en `backend/src/test/resources/`, la web
está en `web/`, y copiar tres archivos JSON es cuestión de segundos. Se resolvió en
cambio configurando Vite para que los lea directamente de donde están.

El motivo es el mismo por el que hoy también se eliminaron las copias duplicadas de
los planes: **una copia no se rompe el día que la hacés, se rompe tres semanas
después**, cuando alguien corrige un diagrama de un lado y el otro sigue con la
versión vieja. Y entonces el backend genera código para un modelo y el lienzo dibuja
otro, sin que nada falle ni avise. Es de los errores más caros de encontrar porque
todo "funciona".

Vale la pena verlo escrito, porque es la clase de razonamiento que se defiende bien:

```ts
// Los diagramas de referencia viven en backend/, congelados desde el Día 1 para
// todas las capas. No se duplican dentro de web/: una copia divergente es un bug
// que aparece tarde y cuesta caro encontrar.
const fixturesDir = path.resolve(import.meta.dirname,
                    '../backend/src/test/resources/reference-diagrams')
```

## 3. La otra decisión, que se paga el Día 8

**El estado de la aplicación está partido en dos, a propósito.**

| Store | Qué guarda | Quién lo conoce |
| :--- | :--- | :--- |
| `canonicalStore` | El diagrama: clases, atributos, relaciones | El servidor. Es lo que se persiste en JSONB |
| `presentationStore` | Qué nodo tenés seleccionado, el zoom, qué panel está abierto | Nadie más. Vive sólo en tu navegador |

Hoy esta separación no sirve para nada visible. Sirve el **Día 8**, cuando entre la
colaboración en tiempo real.

Imaginá que estás con un panel abierto editando los atributos de `Cliente`, y otro
usuario en otra computadora mueve una clase. Llega la mutación por WebSocket y hay que
reemplazar el diagrama con la versión nueva. Si el diagrama y "qué panel tenés
abierto" fueran la misma cosa, **reemplazar uno te cerraría el otro**: cada vez que un
compañero mueve algo, a vos se te cierra el panel y se te pierde la selección.

Con dos stores separados, la mutación remota reemplaza el canónico y **no toca** tu
interfaz. Está registrado como **D-09** y se decidió antes de escribir la primera
línea, que es cuando estas cosas salen gratis. Después salen carísimas.

Detalle de implementación que aprobé: son **dos archivos distintos**, no un store con
dos secciones. La separación queda garantizada por la estructura y no por la
disciplina de quien escribe.

## 4. Una discrepancia real en el contrato congelado

Al escribir los tipos TypeScript apareció algo que nadie había visto. Vale contarlo
porque es exactamente para lo que sirve tener el mismo contrato implementado dos
veces.

En el schema §7, la visibilidad de una **clase** está declarada como opcional y **sin
valor por defecto**. Pero el código Java, cuando no viene, la completa con `PUBLIC`.
Y en TypeScript quedó simplemente opcional. Dos implementaciones del mismo contrato,
dos comportamientos distintos ante el mismo dato ausente.

Hoy no se nota, porque los tres diagramas siempre traen el campo. Se notaría el día
que un modelo venga de la IA, de una foto de pizarra o de un import XMI y lo omita:
el backend generaría código creyendo `PUBLIC` y el lienzo dibujaría la clase sin
símbolo.

### Por qué el schema tiene razón, y la resolución

Mirando §7 completo, la asimetría **no es un descuido**:

| Campo | ¿Obligatorio en §7? | Por qué |
| :--- | :---: | :--- |
| `attributes[].visibility` | **Sí** | Es portante: el generador emite campos `private` con getters según ese valor |
| `methods[].visibility` | **Sí** | Igual: determina si el método sale `public` o no |
| `classes[].visibility` | **No** | No es portante: una entidad JPA generada es `public` siempre. Una clase generada `package-private` no serviría de nada |

O sea: el schema exige el dato donde cambia el código generado, y lo deja libre donde
sólo cambia un símbolo dibujado.

**Resolución (D-16):** el tipo TypeScript se queda opcional —es fiel al schema— y la
normalización a `PUBLIC` va **en un solo lugar**, en el borde donde el modelo entra al
lienzo, no repartida por los componentes. Es el mismo patrón que usa el Java:
normalizar una vez, en la frontera, y que el resto del código no se entere.

**No se modificó §7.** Es el documento de Fase 0 ya entregado y enmendarlo es decisión
de Daniel. La recomendación queda escrita: agregarle `"default": "PUBLIC"` sería una
palabra y cerraría la ambigüedad de raíz.

| # | Decisión | Por qué |

| **D-16** | `classes[].visibility` ausente = `PUBLIC`, normalizado en un solo punto de entrada | El schema la deja opcional a propósito (no afecta al código generado), pero dos capas no pueden interpretar distinto el mismo dato ausente |
